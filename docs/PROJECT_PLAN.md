# PROJECT EUROPE — 작품·대시보드 기획서 (사용자 원안)

> 사용자가 2026-11-11 세션 개설 시 전달한 기획 원문을 정리한 것이다. 이 문서의 결정은 `CONTEXT.md`에 확정 사항으로 옮겨 적는다.

## 1. 작품 개요

- 가제: **《저녁만 먹기로 했잖아요》** · 2017년 유럽 배낭여행 · 19금 성인 로맨틱 코미디 · 옴니버스
- 핵심: 전역 후 처음 떠난 유럽 배낭여행. 혼자 여행하던 24살 대학생이 여행 커뮤니티(네이버 유랑 카페)를 통해 다양한 사람을 만나며 벌어지는 웃기고 아슬아슬한 이야기.
- 집필 원칙: 실제 경험을 출발점으로 삼되 인물·대화·사건을 소설적으로 각색한다. 성인 간의 상호 호감, 관계의 변화, 현실적인 코미디를 중심에 둔다.
- 최종 목표: 노벨피아 연재. **자동 업로드는 공식적으로 허용된 연동 방식이 확인되기 전까지 개발 범위에서 제외**한다. 복사·붙여넣기용 원고 생성과 수동 발행 기록만 만든다.

핵심 흐름: 실제 경험 → 소설적 각색 → 회차 집필 → 설정·인과 검증 → 노벨피아 업로드.

## 2. 대시보드 필수 메뉴 7개

| 메뉴 | 기능 |
|---|---|
| ① 홈 | 집필 진행률, 최근 작업, 다음 할 일 |
| ② 여행썰 보관함 | 실제 경험 기록, 장소·인물·사건·결말 저장 |
| ③ 에피소드 보드 | 각 여행썰을 소설 에피소드로 구성 |
| ④ 원고 편집기 | 회차별 원고 작성, 글자 수, 버전 관리 |
| ⑤ 인물·설정집 | 등장인물, 관계 변화, 여행 일정, 설정 관리 |
| ⑥ AI 검수실 | Claude로 인과·문체·설정·흥미도 검수 |
| ⑦ 연재 관리 | 노벨피아 업로드용 원고, 공개 일정, 조회수 기록 |

**가장 중요한 것: ② 여행썰 보관함과 ③ 에피소드 보드를 분리한다.** 실제로 일어난 일과 소설에서 일어난 일을 따로 기록해야 각색하면서 혼동하지 않는다.

집필 파이프라인(상태): 소재 → 플롯 → 초고 → 검수 → 발행

## 3. 여행썰 데이터 구조 (예)

```
여행썰 #002 · 각색 중
제목: 스위스에서 프라하까지
시기: 2017년 여름        장소: 인터라켄 → 프라하
등장인물: 주인공, 비슷한 나이의 한국인 여성
관계: 첫 만남 → 동행 → 호감 발전
실제 경험: 혼성 도미토리에서 만남. 서로 옷 갈아입는 것이 민망해 방을 나가주었음. 스위스 여행을 함께하다 프라하 일정이 겹쳐 숙소 공유.
소설적 각색: 침대 두 개가 있는 프라하 숙소. 프라하성·카를교·레논벽을 관광하며 호감을 확인하고 결국 한 침대를 쓰게 되는 전개.
미정 사항: 인물 가명, 세부 대화, 사건의 시간 순서, 결말 이후 관계
```

**실제 인물의 이름, 연락처, 사진 등 식별 정보는 저장하지 않는다.** 소설용 가명과 변형된 인물 정보만 쓴다.

## 4. Claude 집필 시스템 (역할 분리)

- **Story Planner**: 여행썰을 입력하면 기승전결, 회차 구성, 반전, 장면별 목표를 설계.
- **Novel Writer**: 승인된 플롯과 설정을 바탕으로 회차 초고 작성. 기존 원고의 문체를 참조.
- **Continuity Checker**: 날짜, 여행 동선, 숙소, 등장인물 관계, 대화의 앞뒤 모순 검출.
- **Reader Appeal Reviewer**: 초반 흡입력, 코미디, 설렘, 성인 로맨스의 긴장감, 다음 화 궁금증 평가.

AI가 원고를 마음대로 덮어쓰지 못한다. 흐름: 사용자가 여행썰 입력 → Claude가 에피소드·회차 플롯 제안 → 사용자 승인·수정 → 초고 생성 → 검수 → 수정안 비교 → 최종 원고 확정 → 발행 대기.

## 5. 기술 아키텍처 (사용자 원안)

| 계층 | 기술 |
|---|---|
| 프런트엔드 | Next.js + TypeScript + Tailwind CSS |
| 백엔드 | FastAPI (Python) |
| DB | SQLite로 시작, 필요 시 PostgreSQL |
| 원고 저장 | Markdown 파일 + Git |
| AI | Claude Code + 선택적 Anthropic API (1차는 API 없이 Claude Code가 Markdown 파일을 직접 관리, AI 버튼은 2차) |
| 배포 | Docker Compose (리눅스 홈서버) |
| 원격 접속 | Tailscale |

권장 폴더 구조(원안): `apps/web`, `apps/api`, `content/{project,experiences,characters,episodes,chapters,timeline}`, `prompts/{planner,writer,continuity,reviewer}.md`, `exports/novelpia`, `CLAUDE.md`, `docker-compose.yml`

> 주의: 서버의 다른 소설 프로젝트(`fullmetal_alchemist`, `religion_novel`)는 Caddy 정적 사이트 + `scripts/build_views.py` 구조로 관리된다. "다른 소설들과 동일하게 관리"하려면 이 구조와 위 원안(Next.js+FastAPI) 중 무엇을 따를지 먼저 정해야 한다 — `CONTEXT.md`의 미정 사항 참고.

## 6. 개발 단계

- **Phase 1 — MVP**: 작품 생성, 여행썰 입력, 에피소드 보드, 원고 편집, 자동 저장, Markdown 내보내기. 완료 기준: 여행썰 2개를 등록하고 회차 원고를 작성·저장할 수 있음.
- **Phase 2 — AI 집필 지원**: 플롯 생성, 초고 생성, 원고 비교, 설정 충돌 검수, 변경 승인.
- **Phase 3 — 노벨피아 연재 관리**: 회차별 공개 상태, 업로드용 원고 생성, 연재 일정, 수동 성과 기록.
- **Phase 4 — 독자 반응 분석**: 회차별 조회수·추천·댓글 반응, 이탈 추정, 제목·도입부 개선 이력.

## 7. 개발 지시서 (사용자 원안)

### 목표
2017년 유럽 배낭여행 경험을 바탕으로 한 성인 로맨틱 코미디 옴니버스 소설을 기획·집필·검수·연재 관리하는 개인용 웹 대시보드. 실제 경험 보관함과 소설 에피소드·원고를 명확히 분리한다. 1차 버전에서는 자동 업로드를 만들지 않는다. 리눅스 홈서버에서 운영하며 PC·모바일에서 모두 쓸 수 있어야 한다.

### 필수 데이터 모델
- **Project**: id, title, genre, synopsis, writing_guidelines, status
- **Experience**: id, title, location, date_or_period, participants(가명 라벨만), factual_summary, notes, privacy_status
- **Episode**: id, project_id, source_experience_ids, title, synopsis, plot, fictional_changes, status, sort_order
- **Chapter**: id, episode_id, number, title, markdown_path, word_count, character_count, status, updated_at
- **Character**: id, fictional_name, age, description, personality, relationship_notes
- **TimelineEvent**: id, location, date_or_period, chapter_id, description
- **Publication**: id, chapter_id, platform, publication_status, published_at, external_url, views, recommendations, comments_count

### 화면
Dashboard / Experiences / Episodes(순서 변경·플롯 편집) / Chapters(Markdown 편집기, 글자 수, 상태) / Characters / Timeline / Publishing

### 집필 원칙
- 실제 경험과 소설적 각색을 구분한다.
- 실제 인물의 개인정보는 저장하지 않는다.
- 등장인물은 모두 성인으로 설정한다.
- 현실적인 여행 코미디와 성인 로맨스를 결합한다.
- 상호 호감, 자연스러운 관계 변화, 코미디, 다음 화에 대한 궁금증을 중요하게 평가한다.
- 원고 작성 전 플롯 승인 단계를 둔다.
- AI 수정 시 기존 원고를 자동으로 덮어쓰지 않는다. 수정 전후 차이를 확인할 수 있어야 한다.

### 초기 샘플 데이터
- **EP01 — 파리 첫 동행**: 2017년 여름, 군 전역 후 첫 유럽 여행을 떠난 24살 남자 대학생. 파리에서 혼자 여행하다 외로움을 느끼고 네이버 유랑 카페로 저녁 동행을 만난다. 남자 둘, 여자 하나가 식사하고 사진을 찍어주고 맥주를 마신 뒤 헤어진다. 주인공은 새로운 사람을 만나는 게 생각보다 쉽다는 걸 깨닫는다.
- **EP02 — 스위스에서 프라하까지**: 인터라켄 혼성 도미토리에서 비슷한 나이의 한국인 여성과 만난다. 첫인상부터 호감이지만 옷을 갈아입을 때는 방을 나가줄 정도로 어색하다. 스위스를 함께 여행하다 프라하 일정이 겹친다. 숙박비를 아끼려 침대 두 개짜리 숙소를 함께 예약한다. 프라하성·카를교·레논벽을 여행하며 사진을 찍어주고 가까워진다. 서로의 호감을 확인하고 한 침대에서 잠드는 방향으로 각색한다.

### 1차 구현 범위
대시보드 기본 레이아웃, 여행썰 CRUD, 에피소드 CRUD·순서 관리, 회차 CRUD, Markdown 원고 편집과 자동 저장, 글자 수 표시, SQLite 영속 저장, Markdown 내보내기, 기본 검색, Docker Compose 실행, 초기 샘플 데이터.

### 구현 품질
모바일 반응형 UI, API 입력 검증, DB 마이그레이션, 저장 실패 시 명확한 오류 표시, 원고 손실 방지, Markdown 파일과 DB 간 동기화 규칙 명시, 주요 API·저장 기능 테스트, README·설치·배포 문서.

### 진행 방식
1) 저장소 구조와 기술 설계 제안 → 2) 데이터 모델과 Markdown 저장 정책 확정 → 3) MVP 단계별 구현 → 4) 샘플 데이터 등록 → 5) 실행·테스트 결과 보고 → 6) AI 기능과 노벨피아 연재 관리는 MVP 이후. 각 단계가 끝날 때 구현 기능, 테스트 결과, 남은 문제를 간략히 보고한다. 최종 목표는 시제품이 아니라 실제 원고를 장기간 안정적으로 관리할 수 있는 웹 애플리케이션이다.

## 8. 운영 방식 (사용자 원안)

소설을 쓰는 Claude와 개발하는 Claude를 구분한다. 개발용은 DB·화면·저장을, 집필용은 `content/`의 설정·에피소드·원고를 읽어 소설을 발전시킨다. **대시보드 구현에 너무 많은 시간을 쓰지 말고**, 1차 MVP가 끝나면 곧바로 파리 편 1~2화와 스위스·프라하 편 집필을 첫 목표로 삼는다. 추후 독자 반응을 기준으로 어떤 유형의 에피소드가 재미있는지 분석하고 다음 여행썰의 배치와 제목을 조정한다.
